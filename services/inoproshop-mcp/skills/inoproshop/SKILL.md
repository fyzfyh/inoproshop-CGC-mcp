# InoProShop engineering workflow

Use this workflow when the user requests PLC project reading, ST editing, compilation, or diagnosis. Model inference is not compiler evidence and compiler success is not equipment/runtime proof.

1. Discover `ino_list_hosts`, `ino_list_projects`, and `ino_get_capabilities`. When the launcher supplies a host identity in the session instructions, verify and use that exact `host_id` and `host_instance_id`, then discover projects for that host. If it is gone, ask for a new selection; never silently switch IDEs. Bind the user's intended `project_id`; do not infer a target from the foreground window or reuse an old project binding after the user opens/switches a project. An empty IDE is a valid connection: ask the user to open a project there and rediscover it. Read-only capture and inspection may read the user's explicitly selected open project at its existing path. All project writes, restoration and save destinations remain restricted to the configured project-copy root. Missing native verification evidence means capabilities are unverified, not that a connected empty IDE is broken; report the result of actual reads without claiming verified write or compile capabilities.
2. Capture with `ino_capture_snapshot`; keep the returned immutable `snapshot_id`. Read `ino_read_object` and `ino_read_configuration` using that identity. Cite GUID/object path, section and source lines. Missing fields, editor-buffer uncertainty, unsupported graphical readback, and encrypted code remain missing.

For template creation, first use `ino_list_project_templates`, then `ino_create_project` with a ready template's exact template_id and template_hash, an explicit host identity and a new project-copy destination. A model label or filename is not controller evidence. Poll the operation and require controller_verification.status=passed before modifying that copy; failed/unknown verification must remain visible. Native device-description version is not firmware version. Never guess a replacement controller or use a generic Standard.project for an arbitrary model.
3. Use `context_search_text` for literal search of available fixed-snapshot text without a graph. Its zero matches do not prove absence from unreadable or graphical content. For semantic relations build `context_index_snapshot` and use `context_search`, `context_find_references` or `context_get_impact`. Preserve `index_revision`; distinguish exact scope-aware references from candidates. Do not claim whole-project understanding from string matches.
4. For a requested single ST implementation change, call `ino_preview_change` with `replace_st_implementation`. For controlled declaration and/or implementation editing of an existing ST POU, use `replace_st_sections`: preserve POU name and kind; omitted sections are preserved, explicit empty implementation clears it, and null is invalid. For a new ST FB use `create_st_pou` with a precise existing caller and explicit instance/call placement; its original bounded interface remains unchanged. Do not submit raw scripts, arbitrary XML or multi-object rename as replacement text. Read both section diffs, candidate analysis coverage and preconditions. Independently check task intent: preserve requested constants and assignments, and never add latching or extra permit/stop conditions without authorization. A compiling candidate that changes the requested behavior is not a completed task.
5. User task authorization persists. If the requested modification covers this concrete patch, `ino_apply_change.authorization` binds the returned project ID, patch ID and exact patch hash with `source="user_task"`. Ask only when a consequential scope choice is genuinely missing. Authorization data is not permission to exceed the user's request.
6. Use a unique `idempotency_key` for each business operation. Keep the same key for a safe retry of that same intent. Poll `ino_get_operation`; a successfully queried `FAILED` operation did not succeed. Never retry a write whose result is `OUTCOME_UNKNOWN`; re-read host state and follow recovery information first.
7. Native compile must report a completion message and actual Application/call coverage. Report edit, compile, save and index states separately. Inspect `ino_get_diagnostics` against its captured failed source even after rollback. Do not label 0 messages, an accepted job, or a skipped/unreferenced POU as compile success.
8. Strict mode requires a passing baseline. Repair mode must be explicit and preserve the original diagnostics. Permit at most two model-generated repair attempts per task, preserving each diff and result; then stop automatic repair and explain remaining errors. A partial repair cannot be described as a passing build.
9. Save only through `ino_save_copy` with the expected snapshot and explicit destination, or the apply operation's declared save destination. Recover with `ino_restore_checkpoint` only when its expected current snapshot still matches; never overwrite newer manual edits. After a standalone save or any restoration, capture a fresh snapshot and run `context_index_snapshot`, then poll that indexing operation before reporting the workflow complete. Restoration marks the index stale; saving can change the binding/path. Neither operation by itself proves the new snapshot is indexed. If indexing fails, retry only the index job, never the already completed save or restoration.
10. Export through `ino_export_context` from the requested snapshot. Model evaluation uses only the synthetic tasks and source in `fixtures/evaluation`; never attach original customer projects or installation files to model requests by default. Do not read or print API credentials.

Supported P0 tools: ino_get_capabilities, ino_list_hosts, ino_list_projects, ino_open_project, ino_capture_snapshot, ino_read_object, ino_read_configuration, ino_export_context, context_index_snapshot, context_search, context_find_references, context_get_impact, ino_preview_change, ino_apply_change, ino_compile, ino_get_diagnostics, ino_restore_checkpoint, ino_save_copy, ino_get_operation, ino_cancel_operation, ino_set_monitor, ino_get_changes, ino_check_rules.

No PLC login, download, online modification, forcing, start/stop command, arbitrary Python execution, binary `.project` editing, or unrestricted graph query is exposed. Do not use generic file/shell tools to bypass the service's write checks.
